\chapter{Introduction}

\section{Project Overview}
\textbf{ComplexityUniverse} is a web platform designed to analyze, visualize, and explain the asymptotic Time and Space complexity (Big-O notation) of computer source code. In computer science and software development, understanding algorithmic efficiency with respect to input size $n$ is essential for writing scalable software.

Traditional static linters only inspect syntax and formatting rules, while dynamic profilers measure wall-clock runtimes on fixed hardware without establishing general mathematical bounds. ComplexityUniverse bridges this gap by pairing Google Gemini AI semantic reasoning with a BCNF-normalized MySQL 8.0 relational database. The platform delivers:
\begin{itemize}
    \item \textbf{Asymptotic Big-O Badging:} Worst, average, and best-case classifications: $\mathcal{O}(1)$, $\mathcal{O}(\log n)$, $\mathcal{O}(n)$, $\mathcal{O}(n \log n)$, $\mathcal{O}(n^2)$, and $\mathcal{O}(2^n)$.
    \item \textbf{Line-by-Line Cost Breakdown:} Clear identification of loop bounds, recursion depth, and auxiliary memory.
    \item \textbf{Actionable Optimization Tips:} Practical guidance for reducing asymptotic bounds.
    \item \textbf{Learn Curriculum Library:} Curated algorithmic topics with runnable code examples and full-text search.
    \item \textbf{Developer Dashboard:} Persistent historical analyses, saved bookmarks, and complexity telemetry.
    \item \textbf{Admin AI Governance Studio:} In-database prompt management with automatic trigger-based version auditing.
\end{itemize}

\section{Problem Statement}
According to Rice's Theorem and the Halting Problem, no general deterministic algorithm can decide non-trivial semantic properties of arbitrary code. Standard compiler AST parsers struggle with dynamic loop termination, recursion trees, and complex standard library functions. At the same time, available developer tools lack persistent relational storage, structured educational tracks, and accessible student workflows. ComplexityUniverse provides a unified platform to analyze, store, and study algorithmic complexity.

\section{Objectives}
The primary objectives of the project are:
\begin{enumerate}
    \item \textbf{Automate Complexity Evaluation:} Integrate Google Gemini with structured JSON output enforcement to evaluate code Time and Space bounds.
    \item \textbf{Provide Granular Code Deconstruction:} Generate line-by-line cost attributions and optimization tips.
    \item \textbf{Architect a BCNF Relational Schema:} Design a 9-table MySQL database strictly adhering to Boyce--Codd Normal Form.
    \item \textbf{Implement Autonomous Business Invariants:} Use MySQL triggers to maintain counters, sanitize inputs, enforce versioning, and log audit events.
    \item \textbf{Deliver High-Speed Analytics via Views:} Construct 5 pre-compiled views to optimize dashboard queries.
    \item \textbf{Integrate Stored Generated Columns:} Compute physical line metrics automatically at the storage engine level.
    \item \textbf{Build a Modern Responsive Interface:} Develop a full-stack Next.js 16 / React 19 web application with Vanilla CSS tokens and canvas particle graphics.
    \item \textbf{Ensure Security \& ACID Transactions:} Enforce SSL database transport encryption, bcrypt hashing, stateless JWT cookies, and ACID transaction boundaries.
\end{enumerate}

\section{Scope of the Project}
The platform supports multi-language code analysis (JavaScript, TypeScript, Python, Java, C, C++, Go, Rust), structured Big-O reporting, user workspaces with persistent histories, a searchable curriculum library, personal bookmarking with notes, and an administrative governance studio. The system operates via static semantic reasoning, avoiding remote code execution risks.

\section{Business Rules}
The operational logic and database constraints are enforced by ten business rules:

\begin{enumerate}[label=\textbf{BR-\arabic*.}]
    \item \textbf{Unique Email:} Every user email must be unique, lowercased, and whitespace-trimmed.
    \item \textbf{Mandatory 1:1 Profile:} Every user must have exactly one profile record, auto-created upon registration via trigger \texttt{trg\_users\_after\_insert}.
    \item \textbf{Cascading Deletion:} Deleting a user must atomically remove their profile, saved analyses, bookmarks, and activity logs via \texttt{ON DELETE CASCADE}.
    \item \textbf{Synchronized Counter:} \texttt{users.analysis\_count} must accurately mirror saved analyses, incrementing on insert and decrementing on delete via triggers.
    \item \textbf{Unique Topic Slug:} Every educational topic must have a unique URL slug, generated automatically from the title if omitted.
    \item \textbf{Bookmark Uniqueness:} A user cannot bookmark the same topic more than once, enforced by a composite unique key on \texttt{(user\_id, topic\_id)}.
    \item \textbf{Role-Based Access:} Admin routes and prompt mutations are restricted to accounts where \texttt{role = 'admin'}.
    \item \textbf{Prompt Version Auditing:} Updating an AI prompt template must automatically increment \texttt{version = version + 1} and refresh \texttt{updated\_at} via a trigger.
    \item \textbf{Immutable Line Count:} \texttt{code\_lines} in \texttt{code\_analyses} must be computed solely by the storage engine using a stored generated expression.
    \item \textbf{Session Security:} API operations modifying user data must verify JWT token identity against the target resource's \texttt{user\_id}.
\end{enumerate}

\chapter{Entity--Relationship (ER) Modeling}

\section{Identification of Entities}
The ComplexityUniverse data model comprises 9 entities:

\begin{enumerate}
    \item \textbf{\texttt{users} (Strong Entity):} Stores user accounts.
    Attributes: \underline{\texttt{id}} (PK), \texttt{name}, \texttt{email} (Unique), \texttt{password\_hash}, \texttt{last\_login\_at}, \texttt{role}, \texttt{status}, \texttt{analysis\_count} (Derived), \texttt{created\_at}, \texttt{updated\_at}.
    \item \textbf{\texttt{user\_profiles} (1:1 Strong Entity):} User profile details.
    Attributes: \underline{\texttt{id}} (PK), \texttt{user\_id} (FK, Unique), \texttt{headline}, \texttt{bio}, \texttt{location}, \texttt{avatar\_seed}.
    \item \textbf{\texttt{analysis\_prompts} (Strong Entity):} Versioned AI prompts.
    Attributes: \underline{\texttt{id}} (PK), \texttt{name}, \texttt{prompt\_template}, \texttt{is\_active}, \texttt{version}, \texttt{updated\_by} (FK), \texttt{created\_at}, \texttt{updated\_at}.
    \item \textbf{\texttt{code\_analyses} (Strong Entity):} Saved analysis reports.
    Attributes: \underline{\texttt{id}} (PK), \texttt{user\_id} (FK), \texttt{title}, \texttt{language}, \texttt{code\_text}, \texttt{code\_lines} (Stored Generated), \texttt{time\_complexity}, \texttt{space\_complexity}, \texttt{summary}, \texttt{detailed\_analysis}, \texttt{detail\_mode}, \texttt{engine}, \texttt{prompt\_version}, \texttt{created\_at}, \texttt{updated\_at}.
    \item \textbf{\texttt{complexity\_topics} (Strong Entity):} Curriculum topics.
    Attributes: \underline{\texttt{id}} (PK), \texttt{topic\_name}, \texttt{slug} (Unique), \texttt{category}, \texttt{difficulty}, \texttt{time\_complexity}, \texttt{space\_complexity}, \texttt{summary}, \texttt{notes\_html}, \texttt{sort\_order}, \texttt{is\_published}, \texttt{created\_at}, \texttt{updated\_at}.
    \item \textbf{\texttt{topic\_examples} (Strong Entity):} Runnable code examples.
    Attributes: \underline{\texttt{id}} (PK), \texttt{topic\_id} (FK), \texttt{title}, \texttt{language}, \texttt{code\_text}, \texttt{analysis\_html}, \texttt{time\_complexity}, \texttt{space\_complexity}, \texttt{sort\_order}, \texttt{created\_at}.
    \item \textbf{\texttt{user\_saved\_topics} (Associative Entity):} Resolves the $M:N$ bookmarking relationship.
    Attributes: \underline{\texttt{id}} (PK), \texttt{user\_id} (FK), \texttt{topic\_id} (FK), \texttt{note}, \texttt{saved\_at}. Composite Key: \texttt{(user\_id, topic\_id)}.
    \item \textbf{\texttt{activity\_log} (Strong Entity):} System audit records.
    Attributes: \underline{\texttt{id}} (PK), \texttt{user\_id} (FK, Nullable), \texttt{action}, \texttt{entity}, \texttt{entity\_id}, \texttt{detail}, \texttt{created\_at}.
    \item \textbf{\texttt{app\_settings} (Strong Entity):} Key-value configuration.
    Attributes: \underline{\texttt{setting\_key}} (PK), \texttt{setting\_value}, \texttt{updated\_at}.
\end{enumerate}

\section{Explanation of the ER Diagram}
\renewcommand{\thefigure}{\thechapter.\arabic{figure}}
The diagrams illustrate the structure and constraints of the database:
\begin{itemize}
    \item \textbf{Conceptual vs. Relational Modeling:} Conceptual diagrams (Fig.~1.1 to 1.5) capture business entities, relationships, and derived attributes (\texttt{analysis\_count}, \texttt{code\_lines} in dashed ellipses) without physical keys. The relational diagrams (Fig.~2.2 to 2.5) materialize primary keys, foreign keys, physical column types, and cascade rules.
    \item \textbf{1:1 Relationship (\texttt{users} to \texttt{user\_profiles}):} Each user has at most one profile, and each profile belongs to exactly one user. Total participation on \texttt{user\_profiles} is enforced by the unique foreign key \texttt{user\_id} with cascade deletion.
    \item \textbf{1:N Relationship (\texttt{users} to \texttt{code\_analyses}):} A user can save multiple analyses ($0..N$). Each analysis record belongs to one user ($1..1$) with cascade deletion.
    \item \textbf{M:N Relationship Resolution (\texttt{users} to \texttt{complexity\_topics}):} Modeled as a direct relationship in Chen notation and mapped into the associative table \texttt{user\_saved\_topics} with two $1:N$ foreign keys and a composite unique constraint on (\texttt{user\_id}, \texttt{topic\_id}).
    \item \textbf{1:N Relationship (\texttt{complexity\_topics} to \texttt{topic\_examples}):} Each curriculum topic includes multiple code examples ($0..N$) with total participation on the examples side.
\end{itemize}

%-------------------- CHAPTER 4 --------------------
\chapter{ER-to-Relational Mapping}

\section{Mapping Rules}
The ER model is converted to relational schemas using standard database mapping rules:
\begin{enumerate}
    \item \textbf{Rule 1 (Strong Entities):} For each strong entity set, create a relation including all simple attributes. Designate a primary key ($\text{PK}$).
    \item \textbf{Rule 2 (Weak Entities):} Include owner entity primary key as a foreign key ($\text{FK}$), with composite primary key where applicable.
    \item \textbf{Rule 3 (Binary 1:1 Relationships):} Include the PK of one entity as an FK in the other (choosing the entity with total participation). Enforce a \texttt{UNIQUE} constraint on the FK column.
    \item \textbf{Rule 4 (Binary 1:N Relationships):} Place the primary key of the ``1'' side as a foreign key in the relation on the ``N'' side.
    \item \textbf{Rule 5 (Binary M:N Relationships):} Create an associative relation containing the primary keys of both participating entities as foreign keys, plus any relationship attributes.
    \item \textbf{Rule 6 (Multivalued Attributes):} Create a separate relation with the attribute and the parent entity's primary key as an FK.
\end{enumerate}

\section{Step-by-Step Conversion}
Applying these rules systematically yields the physical tables:
\begin{enumerate}
    \item \textbf{Step 1: Strong Entities:}
    \begin{itemize}
        \item \texttt{users} maps to \textbf{USERS} (\underline{\texttt{id}}, \texttt{name}, \texttt{email}, \dots) with primary key \texttt{id}.
        \item \texttt{complexity\_topics} maps to \textbf{COMPLEXITY\_TOPICS} (\underline{\texttt{id}}, \texttt{topic\_name}, \texttt{slug}, \dots) with primary key \texttt{id}.
        \item \texttt{app\_settings} maps to \textbf{APP\_SETTINGS} (\underline{\texttt{setting\_key}}, \texttt{setting\_value}, \texttt{updated\_at}) with primary key \texttt{setting\_key}.
    \end{itemize}
    \item \textbf{Step 2: Binary 1:1 Relationship (\texttt{Has\_Profile}):}
    Relation \textbf{USER\_PROFILES} (\underline{\texttt{id}}, \texttt{user\_id}, \dots) includes foreign key \texttt{user\_id} $\rightarrow$ \texttt{users(id)} with constraint \texttt{UNIQUE(user\_id)} and \texttt{ON DELETE CASCADE}.
    \item \textbf{Step 3: Binary 1:N Relationships:}
    \begin{itemize}
        \item \textbf{CODE\_ANALYSES} includes foreign key \texttt{user\_id} $\rightarrow$ \texttt{users(id)} with \texttt{ON DELETE CASCADE}.
        \item \textbf{TOPIC\_EXAMPLES} includes foreign key \texttt{topic\_id} $\rightarrow$ \texttt{complexity\_topics(id)} with \texttt{ON DELETE CASCADE}.

\chapter{Database Normalization}

\section{Unnormalized Form (UNF)}
A monolithic unnormalized relation exhibits operational anomalies:
\[
\textbf{UNF\_PLATFORM} (\texttt{user\_id}, \texttt{email}, \{\texttt{analyses}\}, \{\texttt{bookmarks}\})
\]
\begin{enumerate}
    \item \textbf{Insertion Anomaly:} New educational topics cannot be recorded without an existing user bookmark.
    \item \textbf{Update Anomaly:} Changing user details requires updating all historical analysis rows.
    \item \textbf{Deletion Anomaly:} Deleting a user's sole analysis risks deleting account credentials.
\end{enumerate}

\section{First Normal Form (1NF)}
\textbf{Condition:} All attribute values are atomic; no repeating groups.
Decomposing nested arrays into individual relations guarantees scalar columns (integers, strings, timestamps), placing all tables in 1NF.

\section{Second Normal Form (2NF)}
\textbf{Condition:} The relation is in 1NF and no non-prime attribute depends on a proper subset of any candidate key.
Tables with single-attribute candidate keys satisfy 2NF trivially. In \texttt{user\_saved\_topics}, the candidate key is composite: \{\texttt{user\_id}, \texttt{topic\_id}\}. The non-prime attributes (\texttt{note}, \texttt{saved\_at}) depend on both attributes together, satisfying 2NF.

\section{Third Normal Form (3NF)}
\textbf{Condition:} In every dependency $X \rightarrow A$, either $X$ is a superkey or $A$ is a prime attribute.
No non-prime attribute determines another non-prime attribute in any table. Transitive dependencies are absent, satisfying 3NF.

\section{Boyce--Codd Normal Form (BCNF)}
\textbf{Condition:} For every non-trivial dependency $X \rightarrow A$, $X$ must be a superkey.
In all 9 relations, every determinant is a primary key or candidate key:
\begin{itemize}
    \item \texttt{users}: Determinants \{\texttt{id}\} and \{\texttt{email}\} are both candidate keys $\implies$ \textbf{BCNF}.
    \item \texttt{user\_profiles}: Determinants \{\texttt{id}\} and \{\texttt{user\_id}\} are candidate keys $\implies$ \textbf{BCNF}.
    \item \texttt{complexity\_topics}: Determinants \{\texttt{id}\} and \{\texttt{slug}\} are candidate keys $\implies$ \textbf{BCNF}.
    \item \texttt{user\_saved\_topics}: Determinants \{\texttt{id}\} and \{\texttt{user\_id}, \texttt{topic\_id}\} are candidate keys $\implies$ \textbf{BCNF}.
    \item All other tables have single primary key determinants $\implies$ \textbf{BCNF}.
\end{itemize}

\chapter{Relational Integrity and Constraints}

Relational constraints maintain database consistency across concurrent operations:
\begin{enumerate}
    \item \textbf{Domain Constraints:} Enforce data types and ranges:
    \begin{itemize}
        \item \textit{Integers:} \texttt{TINYINT UNSIGNED} (prompt versions), \texttt{INT UNSIGNED} (users, topics), \texttt{BIGINT UNSIGNED} (logs, analyses).
        \item \textit{Enums:} \texttt{ENUM('user', 'admin')}, \texttt{ENUM('active', 'suspended')}, \texttt{ENUM('Beginner', 'Intermediate', 'Advanced')}, \texttt{ENUM('short', 'detailed')}.
        \item \textit{Strings:} \texttt{VARCHAR(190)} for emails (compatible with utf8mb4 unique indexing).
    \end{itemize}
    \item \textbf{Primary Key Constraints:} Explicit primary keys on all tables (\texttt{id} or \texttt{setting\_key}) create clustered B+Tree indexes.
    \item \textbf{Foreign Key Constraints:} 7 explicit foreign keys preserve referential integrity:
    \begin{itemize}
        \item \texttt{user\_profiles(user\_id)} $\rightarrow$ \texttt{users(id)}
        \item \texttt{code\_analyses(user\_id)} $\rightarrow$ \texttt{users(id)}
        \item \texttt{topic\_examples(topic\_id)} $\rightarrow$ \texttt{complexity\_topics(id)}
        \item \texttt{user\_saved\_topics(user\_id)} $\rightarrow$ \texttt{users(id)}
        \item \texttt{user\_saved\_topics(topic\_id)} $\rightarrow$ \texttt{complexity\_topics(id)}
        \item \texttt{activity\_log(user\_id)} $\rightarrow$ \texttt{users(id)}
        \item \texttt{analysis\_prompts(updated\_by)} $\rightarrow$ \texttt{users(id)}
    \end{itemize}
    \item \textbf{\texttt{UNIQUE} Constraints:}
    \begin{itemize}
        \item \texttt{uq\_users\_email}: Enforces unique user email addresses.
        \item \texttt{uq\_profile\_user}: Enforces 1:1 user-to-profile cardinality.
        \item \texttt{uq\_topics\_slug}: Guarantees unique URL paths for curriculum topics.
        \item \texttt{uq\_saved\_user\_topic}: Composite uniqueness on (\texttt{user\_id}, \texttt{topic\_id}).
    \end{itemize}
    \item \textbf{\texttt{NOT NULL} Constraints:} Enforced on mandatory operational fields (\texttt{email}, \texttt{password\_hash}, \texttt{code\_text}, \texttt{time\_complexity}, \texttt{topic\_name}).
    \item \textbf{Referential Actions:} \texttt{ON DELETE CASCADE} purges dependent rows when a user or topic is removed; \texttt{ON DELETE SET NULL} retains prompt records if an admin account is purged.
\end{enumerate}

\section{SQL Query Implementation}
Ten SQL queries demonstrating required curriculum concepts:

\paragraph{Query 1: Simple SELECT with Filtering}
Retrieve published educational topics under ``Searching'' with Beginner difficulty:
\begin{lstlisting}[language=SQL]
SELECT id, topic_name, slug, difficulty, time_complexity
  FROM complexity_topics
 WHERE is_published = 1 AND category = 'Searching' AND difficulty = 'Beginner';
\end{lstlisting}

\paragraph{Query 2: Sorting using ORDER BY}
Retrieve analyses sorted by line count and creation date descending:
\begin{lstlisting}[language=SQL]
SELECT id, user_id, title, language, code_lines, time_complexity, created_at
  FROM code_analyses
 ORDER BY code_lines DESC, created_at DESC LIMIT 10;
\end{lstlisting}

\paragraph{Query 3: Aggregate Functions (COUNT, AVG, MIN, MAX)}
Compute aggregate line metrics across stored analyses:
\begin{lstlisting}[language=SQL]
SELECT COUNT(*) AS total_analyses, AVG(code_lines) AS avg_lines,
       MIN(code_lines) AS min_lines, MAX(code_lines) AS max_lines
  FROM code_analyses;
\end{lstlisting}

\paragraph{Query 4: Grouping with GROUP BY and HAVING}
Group analyses by time complexity and filter classes with at least 2 occurrences:
\begin{lstlisting}[language=SQL]
SELECT time_complexity, COUNT(*) AS total_count, ROUND(AVG(code_lines), 1) AS avg_lines
  FROM code_analyses
 GROUP BY time_complexity
HAVING total_count >= 2
 ORDER BY total_count DESC;
\end{lstlisting}

\paragraph{Query 5: Table Joins (INNER and LEFT JOIN)}
Retrieve user profiles along with total saved bookmarks:
\begin{lstlisting}[language=SQL]
SELECT u.id, u.name, u.email, p.headline, COUNT(s.id) AS total_bookmarks
  FROM users u
  LEFT JOIN user_profiles p ON p.user_id = u.id
  LEFT JOIN user_saved_topics s ON s.user_id = u.id
 GROUP BY u.id, u.name, u.email, p.headline;
\end{lstlisting}

\paragraph{Query 6: Nested Subquery}
Find users whose personal analysis count exceeds the platform average:
\begin{lstlisting}[language=SQL]
SELECT id, name, email, analysis_count FROM users
 WHERE analysis_count > (SELECT AVG(analysis_count) FROM users);
\end{lstlisting}

\paragraph{Query 7: Set Membership using EXISTS}
Find topics bookmarked by administrators using an \texttt{EXISTS} subquery:
\begin{lstlisting}[language=SQL]
SELECT t.id, t.topic_name, t.category FROM complexity_topics t
 WHERE EXISTS (
   SELECT 1 FROM user_saved_topics s JOIN users u ON u.id = s.user_id
    WHERE s.topic_id = t.id AND u.role = 'admin'
 );
\end{lstlisting}

\paragraph{Query 8: Multi-Table Join across Three Relations}
Join users, bookmarks, and curriculum topics to display study notes:
\begin{lstlisting}[language=SQL]
SELECT u.name AS student_name, t.topic_name, s.note, s.saved_at
  FROM user_saved_topics s
  JOIN users u ON u.id = s.user_id
  JOIN complexity_topics t ON t.id = s.topic_id
 ORDER BY s.saved_at DESC;
\end{lstlisting}

\paragraph{Query 9: Business Intelligence Query (Algorithmic Cost Distribution)}
Categorize analyses into performance tiers using a \texttt{CASE} statement:
\begin{lstlisting}[language=SQL]
SELECT CASE
         WHEN time_complexity IN ('O(1)', 'O(log n)') THEN 'Fast (Optimal)'
         WHEN time_complexity IN ('O(n)', 'O(n log n)') THEN 'Linear / Linearithmic'
         WHEN time_complexity IN ('O(n^2)', 'O(n^3)') THEN 'Polynomial (Heavy)'
         ELSE 'Exponential / Severe'
       END AS algorithmic_grade,
       COUNT(*) AS total_algorithms,
       ROUND(COUNT(*) * 100.0 / (SELECT COUNT(*) FROM code_analyses), 2) AS percentage_share
  FROM code_analyses GROUP BY algorithmic_grade ORDER BY total_algorithms DESC;
\end{lstlisting}

\paragraph{Query 10: Analytical View Query}
Query the pre-compiled \texttt{v\_user\_overview} view for user rank metrics:
\begin{lstlisting}[language=SQL]
SELECT id, name, email, headline, rank_label, saved_topic_count
  FROM v_user_overview WHERE status = 'active';
\end{lstlisting}

\subsection{Database Triggers}
Ten triggers enforce rules autonomously at the database layer:
\begin{itemize}
    \item \texttt{trg\_users\_before\_insert} / \texttt{update}: Normalizes emails to lowercase.
    \item \texttt{trg\_users\_after\_insert}: Auto-provisions matching \texttt{user\_profiles} and logs registration.
    \item \texttt{trg\_analyses\_after\_insert} / \texttt{delete}: Increments/decrements \texttt{users.analysis\_count}.
    \item \texttt{trg\_topics\_before\_insert} / \texttt{update}: Auto-generates URL slugs from titles.
    \item \texttt{trg\_saved\_after\_insert} / \texttt{delete}: Records bookmark audit events.
    \item \texttt{trg\_prompt\_before\_update}: Automatically increments prompt version by 1 upon editing (managed via the Admin AI Studio, Fig.~\ref{fig:ui_admin_prompts}).
\end{itemize}

CREATE TRIGGER trg_prompt_before_update
BEFORE UPDATE ON analysis_prompts FOR EACH ROW

  SET NEW.version    = OLD.version + 1;

END$$
DELIMITER ;
\end{lstlisting}

ComplexityUniverse demonstrates the successful design, normalization, cloud deployment, and full-stack integration of an industrial DBMS:
\begin{itemize}
    \item Architected a 9-table MySQL 8.0 database strictly adhering to Boyce--Codd Normal Form (BCNF).

\section{Limitations}
\begin{enumerate}
    \item \textbf{Single-File Scope:} Analyzes self-contained functions; multi-file repository dependency graphs are not yet resolved.
    \item \textbf{AI API Dependency:} Evaluation throughput depends on Gemini API response latency.
    \item \textbf{Halting Problem Boundary:} Highly obfuscated code can only be evaluated asymptotically through probabilistic reasoning.
\end{enumerate}
