\chapter{Introduction}

\section{Project Overview}
\textbf{ComplexityUniverse} is an end-to-end cloud platform designed to analyze, explain, and visualize the computational complexity (asymptotic Time and Space complexity in Big-O notation) of arbitrary computer source code. In computer science education and professional software engineering, understanding how algorithms scale with respect to input size $n$ is fundamental to producing performant, scalable software.

Traditional static analysis tools such as linters (e.g., ESLint, Checkstyle, SonarQube) inspect syntactic patterns, formatting rules, and code smells; however, they cannot deduce mathematical recurrence relations, iteration bounds, or recursion trees. Conversely, dynamic profilers (such as Valgrind, gprof, or browser DevTools) measure wall-clock milliseconds and memory allocation on a single execution machine with specific test inputs; however, they cannot derive the generalized mathematical Big-O bounds governing unbounded input sizes.

ComplexityUniverse bridges this fundamental divide by combining Large Language Model (LLM) semantic reasoning (powered by Google Gemini API) with a rigorously engineered, BCNF-normalized relational database management system (MySQL 8.0 on Aiven Cloud). The system computes:
\begin{itemize}
    \item \textbf{Asymptotic Big-O Badging:} Worst-case, average-case, and best-case classifications ($\mathcal{O}(1), \mathcal{O}(\log n), \mathcal{O}(n), \mathcal{O}(n \log n), \mathcal{O}(n^2), \mathcal{O}(2^n)$).
    \item \textbf{Line-by-Line Cost Breakdown:} Deconstructing loops, recursive invocations, and auxiliary memory allocations down to exact code line numbers.
    \item \textbf{Bottlenecks \& Optimization Suggestions:} Actionable algorithmic redesign patterns (e.g., converting an $\mathcal{O}(n^2)$ nested loop into an $\mathcal{O}(n)$ hash-map index).
    \item \textbf{Interactive Educational Curriculum:} A rich Learn Library containing pre-seeded fundamental data structures and algorithmic paradigms with full-text search.
    \item \textbf{Developer Dashboard:} Persistent historical analyses, saved educational bookmarks, and complexity distribution analytics.
    \item \textbf{Administrative AI Studio:} In-database prompt template management, automated schema-level version auditing via triggers, and live LLM model selection.
\end{itemize}

The intended users encompass computer science undergraduate students, software engineering professionals, competitive programmers preparing for technical interviews, and university faculty demonstrating algorithmic scalability.

\section{Problem Statement}
In theoretical computer science, Rice's Theorem and Alan Turing's Halting Problem prove that:
\[
\text{No general deterministic algorithm can decide any non-trivial semantic property of arbitrary source code.}
\]
Consequently, calculating exact run-time asymptotic complexity through traditional compiler abstract syntax trees (ASTs) fails when programs involve:
\begin{enumerate}
    \item Dynamic or data-dependent loop termination conditions (e.g., \texttt{while (x > 0)});
    \item Non-trivial recursion trees with branching factors and variable divide-and-conquer divisions;
    \item High-level language standard libraries whose internal algorithmic costs (e.g., Python's Timsort $\mathcal{O}(n \log n)$, JavaScript's array operations) require deep semantic context beyond AST node counting.
\end{enumerate}

Existing commercial developer platforms either ignore asymptotic complexity entirely or lock algorithmic insights behind high-cost proprietary systems without relational persistence or educational workflows. Students and developers lack a unified, accessible platform where arbitrary code can be evaluated, cataloged, historically indexed, and studied alongside canonical algorithmic paradigms.

\section{Objectives}
The core engineering and academic objectives of the ComplexityUniverse project are:
\begin{enumerate}
    \item \textbf{Automate Asymptotic Complexity Evaluation:} Develop an AI gateway utilizing Google Gemini with structured JSON output enforcement to accurately determine Time and Space complexity bounds.
    \item \textbf{Provide Granular Code Deconstructions:} Extract line-by-line cost attributions, recurrence formulations, and concrete optimization recommendations for arbitrary source code.
    \item \textbf{Architect a BCNF Relational Database:} Design and implement a 9-table relational database schema on MySQL 8.0 strictly adhering to Boyce--Codd Normal Form to eliminate insertion, update, and deletion anomalies.
    \item \textbf{Implement Autonomous Business Invariants:} Leverage MySQL triggers to maintain user activity counters, normalize user inputs (emails and slugs), auto-provision profiles, enforce prompt template versioning, and record immutable audit logs.
    \item \textbf{Deliver High-Speed Analytics via Views:} Construct 5 pre-compiled analytical MySQL views to eliminate expensive multi-table joins on high-traffic client dashboard and feed endpoints.
    \item \textbf{Integrate Generated Stored Columns:} Utilize MySQL 8.0 stored generated columns to evaluate physical code line counts at the storage engine layer without application-level overhead.
    \item \textbf{Build an Engaging Modern Interface:} Develop a responsive full-stack web application using Next.js 16 App Router, React 19, Vanilla CSS design tokens, and an HTML5 2D Canvas particle simulation.
    \item \textbf{Ensure Enterprise Security \& ACID Integrity:} Enforce TLS/SSL database transport encryption, stateless JWT authentication via secure \texttt{httpOnly} cookies, bcrypt password hashing, and ACID transaction boundaries.
\end{enumerate}

\section{Scope of the Project}
The functional scope of ComplexityUniverse encompasses:
\begin{itemize}
    \item \textbf{Multi-Language Static Analysis:} Analysis of arbitrary code written in JavaScript, TypeScript, Python, Java, C, C++, Go, and Rust.
    \item \textbf{Structured Algorithmic Profiling:} Extraction of Big-O notations, asymptotic explanations, loop analysis, space breakdown, and optimization tips.
    \item \textbf{Persistent User Workspaces:} User account registration, secure authentication, profile management, and persistent storage of personal analysis histories.
    \item \textbf{Educational Curriculum (Learn Library):} Categorized modules covering asymptotic fundamentals, sorting, searching, trees, graphs, and dynamic programming, searchable via MySQL \texttt{FULLTEXT} indexes.
    \item \textbf{Personalized Bookmarking System:} Associative $M:N$ entity modeling allowing users to bookmark curriculum topics with custom personal notes.
    \item \textbf{Administrative Governance Studio:} Role-based access control (RBAC) enabling administrators to inspect system telemetry, manage user accounts, alter AI prompt templates with automatic version incrementation, and select active Gemini models.
\end{itemize}

\noindent\textbf{Scope Boundaries:} The system deliberately avoids executing submitted code inside a native operating system sandbox to prevent remote code execution (RCE) vulnerabilities; all analysis is conducted statically via semantic reasoning. Multi-file enterprise monorepo analysis is reserved for future revisions.

    \end{itemize}
    \item \textbf{Storage Engine Code Metrics:}
    \begin{itemize}

    \begin{itemize}
        \item Authenticated users shall be able to save analyses into their private workspace.
        \item Users shall be able to retrieve, view, search, and delete their saved analyses with automatic pagination.

    \item \textbf{Curriculum \& Learn Library:}
    \begin{itemize}

\section{Business Rules}
The operational logic and database constraints are governed by the following formal business rules:

\begin{enumerate}[label=\textbf{BR-\arabic*.}]
    \item \textbf{Unique Email Identity:} Each registered user must possess a unique email address. The system must automatically normalize all email addresses to lowercase and strip whitespace prior to storage.
    \item \textbf{Mandatory 1:1 Profile Existence:} Every user record in \texttt{users} must correspond to exactly one profile row in \texttt{user\_profiles}. When a user registers, the database trigger \texttt{trg\_users\_after\_insert} must automatically instantiate a matching \texttt{user\_profiles} record.
    \item \textbf{Referential Integrity \& Cascading Deletion:} Deleting a user must immediately and atomically delete their associated profile, saved analyses, bookmarks, and activity log entries via \texttt{ON DELETE CASCADE} constraints, preventing orphaned foreign key references.
    \item \textbf{Non-Negative Real-Time Analysis Counter:} The attribute \texttt{users.analysis\_count} must always accurately reflect the current number of valid analyses associated with the user in \texttt{code\_analyses}. The counter must increment on \texttt{INSERT} and decrement on \texttt{DELETE} via triggers, never falling below zero.
    \item \textbf{Automated Slug Normalization:} Every educational curriculum topic must possess a unique, lowercase, hyphen-delimited URL slug derived automatically from the topic title if not explicitly provided.
    \item \textbf{Bookmark Uniqueness:} A user cannot bookmark the same educational topic more than once. This invariant is enforced by a composite unique constraint on \texttt{(user\_id, topic\_id)}.
    \item \textbf{Strict Role-Based Authorization:} System administration routes and prompt mutation endpoints must be restricted exclusively to users with \texttt{role = 'admin'}.
    \item \textbf{Automated Prompt Version Auditing:} Whenever an administrative user updates an existing record in \texttt{analysis\_prompts}, the \texttt{version} attribute must increment automatically by 1, and the \texttt{updated\_at} timestamp must update to the current time via a \texttt{BEFORE UPDATE} trigger.
    \item \textbf{Code Metric Immutability:} The \texttt{code\_lines} attribute in \texttt{code\_analyses} must be strictly computed from the byte length and newline character count of the stored \texttt{code\_text} via a MySQL stored generated expression, preventing manual alteration.
    \item \textbf{Stateless Session Security:} Client sessions must never store sensitive database credentials or unhashed passwords. All API requests modifying user-owned data must verify JWT token identity against the target resource's \texttt{user\_id}.
\end{enumerate}

\chapter{ER-to-Relational Mapping}

\section{Mapping Rules}
The formal ER-to-Relational mapping process maps conceptual constructs into relational schemas according to standard database theory (Elmasri \& Navathe, Silberschatz et al.):

\begin{enumerate}
    \item \textbf{Rule 1 (Strong Entities):} For each strong entity set $E$, create a relation $R$ containing all simple attributes of $E$. Choose one key attribute as the Primary Key ($\text{PK}$).
    \item \textbf{Rule 2 (Weak Entities):} For each weak entity $W$ with owner entity $O$, create a relation $R$ containing all simple attributes of $W$, and include the primary key of $O$ as a foreign key ($\text{FK}$) in $R$. The primary key of $R$ is the composite of owner key and partial key.
    \item \textbf{Rule 3 (Binary 1:1 Relationships):} Identify relations $S$ and $T$. Include the primary key of $S$ as a foreign key in $T$ (preferably choosing the entity with total participation). Add a \texttt{UNIQUE} constraint on the foreign key column to preserve the $1:1$ cardinality.
    \item \textbf{Rule 4 (Binary 1:N Relationships):} For a relationship type $R$ between entity $S$ (the ``1'' side) and entity $T$ (the ``N'' side), include the primary key of $S$ as a foreign key in relation $T$.
    \item \textbf{Rule 5 (Binary M:N Relationships):} For an $M:N$ relationship $R$ between entities $S$ and $T$, create a new associative relation $R_{rel}$. Include the primary keys of both $S$ and $T$ as foreign keys in $R_{rel}$. Include all relationship attributes of $R$. The primary key of $R_{rel}$ is formed by the combination of foreign keys, or a surrogate key backed by a composite unique constraint.
    \item \textbf{Rule 6 (Multivalued Attributes):} For each multivalued attribute, create a new relation containing the attribute and the primary key of the parent entity as a foreign key.
\end{enumerate}

\section{Candidate Keys and Attribute Classification}
An attribute set $K \subseteq R$ is a \textbf{Candidate Key} if:
\begin{enumerate}
    \item $K \rightarrow R$ holds under the attribute closure $K^+$ (Sufficiency);
    \item For every proper subset $K' \subset K$, $K' \rightarrow R$ does not hold (Minimality).
\end{enumerate}

Attributes belonging to any candidate key are termed \textbf{Prime Attributes}; all remaining attributes are \textbf{Non-Prime Attributes}.

\subsection{Mathematical Attribute Closure Proofs}
We demonstrate the attribute closure derivations for key relations using Armstrong's Axioms:

\begin{itemize}
    \item \textbf{Closure of \texttt{\{email\}} in \texttt{users}:}
    \begin{align*}
        \{\text{email}\}^+ &= \{\text{email}\} \quad (\text{by Reflexivity}) \\
        &= \{\text{email}\} \cup \{\text{id}, \text{name}, \text{password\_hash}, \text{last\_login\_at}, \\
        &\qquad\qquad\quad\; \text{role}, \text{status}, \text{analysis\_count}, \text{created\_at}, \text{updated\_at}\} \quad (\text{by } \mathrm{FD}_2) \\
        &= R_{\text{users}}
    \end{align*}
    Since no proper subset of $\{\text{email}\}$ exists, \texttt{email} is a minimal Candidate Key.
    \item \textbf{Closure of \texttt{\{user\_id, topic\_id\}} in \texttt{user\_saved\_topics}:}
    \begin{align*}
        \{\text{user\_id, topic\_id}\}^+ &= \{\text{user\_id, topic\_id}\} \quad (\text{by Reflexivity}) \\
        &= \{\text{user\_id, topic\_id}\} \cup \{\text{id}, \text{note}, \text{saved\_at}\} \quad (\text{by } \mathrm{FD}_2) \\
        &= R_{\text{user\_saved\_topics}}
    \end{align*}
    Testing proper subsets:
    \begin{itemize}
        \item $\{\text{user\_id}\}^+ = \{\text{user\_id}\} \neq R$ (a user can save multiple topics);
        \item $\{\text{topic\_id}\}^+ = \{\text{topic\_id}\} \neq R$ (a topic can be saved by multiple users).
    \end{itemize}

\end{itemize}

\section{FD Analysis}
Every functional dependency identified above is grounded in real-world application invariants:
\begin{itemize}
    \item \textbf{Email Uniqueness in \texttt{users}:} In a modern web platform, an email represents a globally unique authentication credential. Therefore, knowing the email uniquely identifies the exact student tuple ($FD_2$).
    \item \textbf{Composite Invariant in \texttt{user\_saved\_topics}:} A student either has bookmarked a specific curriculum topic or has not. They cannot bookmark the same topic under two conflicting notes; thus, the pair $(\text{user\_id}, \text{topic\_id})$ deterministically resolves the bookmark instance ($FD_2$).
    \item \textbf{Slug Invariant in \texttt{complexity\_topics}:} Web routing in Next.js relies on unique URL paths (e.g., \texttt{/learn/binary-search}). Consequently, the URL slug uniquely resolves the curriculum record ($FD_2$).
\end{itemize}

\chapter{Database Normalization}

Database normalization is the formal mathematical process of decomposing relations to eliminate insertion, update, and deletion anomalies while eliminating unnecessary data redundancy.

\section{Unnormalized Form (UNF)}
Consider a hypothetical unnormalized monolithic relation $\text{UNF\_PLATFORM}$ representing the entire system:
\begin{verbatim}
UNF_PLATFORM(user_id, user_name, user_email, user_bio,
             {analyses: [analysis_id, code_text, time_comp, space_comp]},
             {bookmarks: [topic_id, topic_name, note]})
\end{verbatim}

\noindent\textbf{Anomalies inherent in UNF:}
\begin{enumerate}
    \item \textbf{Insertion Anomaly:} A new curriculum topic (e.g., ``Dijkstra's Algorithm'') cannot be added to the platform until at least one user registers and saves it as a bookmark.
    \item \textbf{Update Anomaly:} If a user modifies their account name or email, dozens of rows containing historical analyses must be redundantly updated. Any missed update creates inconsistent database states.
    \item \textbf{Deletion Anomaly:} If a user deletes their sole saved code analysis, deleting the tuple accidentally deletes the user's account credentials and profile biography.
\end{enumerate}

\section{First Normal Form (1NF)}
\textbf{Formal Condition:} A relation $R$ is in 1NF if and only if all underlying domains contain only atomic (indivisible) scalar values, and there are no repeating groups or nested relation arrays.

\noindent\textbf{Conversion to 1NF:}
The repeating groups \texttt{analyses} and \texttt{bookmarks} are decomposed into separate relations. Multi-valued and nested structures are eliminated, ensuring every column contains single scalar data types (integers, varchars, timestamps).

\section{Second Normal Form (2NF)}
\textbf{Formal Condition:} A relation $R$ is in 2NF if and only if it is in 1NF and no non-prime attribute is partially dependent on any candidate key of $R$. Formally:
\[
\forall (X \rightarrow A) \in F, \quad A \notin \text{Prime}(R) \implies \nexists K \in \text{CK}(R) \text{ such that } X \subset K.
\]

\noindent\textbf{Analysis:}
\begin{itemize}
    \item For relations with single-attribute candidate keys (\texttt{users}, \texttt{user\_profiles}, \texttt{analysis\_prompts}, \texttt{code\_analyses}, \texttt{complexity\_topics}, \texttt{topic\_examples}, \texttt{activity\_log}, \texttt{app\_settings}), proper subsets of candidate keys cannot exist. Thus, partial dependencies are mathematically impossible.
    \item In relation \texttt{user\_saved\_topics}, the candidate key is composite: $\{\text{user\_id, topic\_id}\}$. The non-prime attributes are \texttt{note} and \texttt{saved\_at}. A personal note applies strictly to the specific pairing of a user bookmarking a topic. Neither $\text{user\_id} \rightarrow \text{note}$ nor $\text{topic\_id} \rightarrow \text{note}$ holds. Hence, partial dependency does not exist, and 2NF is satisfied.
\end{itemize}

\section{Third Normal Form (3NF)}
\textbf{Formal Condition:} A relation $R$ is in 3NF if and only if it is in 2NF and for every non-trivial functional dependency $X \rightarrow A$, at least one of the following holds:
\begin{enumerate}
    \item $X$ is a superkey of $R$;
    \item $A$ is a prime attribute of $R$ (Transitivity defense).
\end{enumerate}

\noindent\textbf{Analysis:}
In all 9 relations, every determinant attribute set $X$ is either the primary key or a candidate key (superkey). No non-prime attribute determines another non-prime attribute. Therefore, transitive dependencies are completely absent, and 3NF is fully satisfied.

\section{Boyce--Codd Normal Form (BCNF)}
\textbf{Formal Condition:} A relation $R$ is in BCNF if and only if for every non-trivial functional dependency $X \rightarrow A$, $X$ is a superkey of $R$. BCNF eliminates all anomalies that 3NF allows when candidate keys overlap.

\noindent\textbf{Rigorous Table-by-Table Verification:}
\begin{itemize}
    \item \textbf{\texttt{users}:} Determinants are $\{\text{id}\}$ and $\{\text{email}\}$. Both are candidate keys $\implies$ \textbf{Satisfies BCNF}.
    \item \textbf{\texttt{user\_profiles}:} Determinants are $\{\text{id}\}$ and $\{\text{user\_id}\}$. Both are candidate keys $\implies$ \textbf{Satisfies BCNF}.
    \item \textbf{\texttt{analysis\_prompts}:} Determinant is $\{\text{id}\}$ (candidate key) $\implies$ \textbf{Satisfies BCNF}.
    \item \textbf{\texttt{code\_analyses}:} Determinant is $\{\text{id}\}$ (candidate key) $\implies$ \textbf{Satisfies BCNF}.
    \item \textbf{\texttt{complexity\_topics}:} Determinants are $\{\text{id}\}$ and $\{\text{slug}\}$. Both are candidate keys $\implies$ \textbf{Satisfies BCNF}.
    \item \textbf{\texttt{topic\_examples}:} Determinant is $\{\text{id}\}$ (candidate key) $\implies$ \textbf{Satisfies BCNF}.
    \item \textbf{\texttt{user\_saved\_topics}:} Determinants are $\{\text{id}\}$ and $\{\text{user\_id, topic\_id}\}$. Both are candidate keys $\implies$ \textbf{Satisfies BCNF}.
    \item \textbf{\texttt{activity\_log}:} Determinant is $\{\text{id}\}$ (candidate key) $\implies$ \textbf{Satisfies BCNF}.
    \item \textbf{\texttt{app\_settings}:} Determinant is $\{\text{setting\_key}\}$ (candidate key) $\implies$ \textbf{Satisfies BCNF}.
\end{itemize}

By the Lossless Decomposition Theorem, the join reconstructs the original instance without spurious tuples.

\chapter{Relational Integrity and Constraints}

Relational integrity constraints enforce database validity, prevent invalid state transitions, and guarantee consistency across concurrent web operations:

\begin{enumerate}
    \item \textbf{Domain Constraints:}
    Attributes are restricted to rigorous physical data types matching their domain:
    \begin{itemize}
        \item Integer domains: \texttt{TINYINT UNSIGNED} (1 byte, 0--255) for prompt versions, \texttt{INT UNSIGNED} (4 bytes) for users and topics, \texttt{BIGINT UNSIGNED} (8 bytes) for high-volume logs and analyses.
        \item String domains: \texttt{VARCHAR(190)} for emails (compatible with InnoDB utf8mb4 indexing limits), \texttt{VARCHAR(255)} for secure bcrypt hashes.
        \item Categorical constraints: \texttt{ENUM('user', 'admin')} in \texttt{users}, \texttt{ENUM('active', 'suspended')} in \texttt{users}, \texttt{ENUM('Beginner', 'Intermediate', 'Advanced')} in \texttt{complexity\_topics}, \texttt{ENUM('short', 'detailed')} in \texttt{code\_analyses}.
    \end{itemize}
    \item \textbf{Primary Key Constraints:}
    Every table defines an explicit primary key using \texttt{PRIMARY KEY (id)} or \texttt{PRIMARY KEY (setting\_key)}. This guarantees that entity tuples remain distinctly addressable, and InnoDB creates clustered B+Tree indexes on these columns.
    \item \textbf{Foreign Key Constraints:}
    A total of 7 explicit foreign key constraints preserve referential integrity:
    \begin{itemize}
        \item \texttt{fk\_profile\_user}: \texttt{user\_profiles.user\_id} $\rightarrow$ \texttt{users.id};
        \item \texttt{fk\_analyses\_user}: \texttt{code\_analyses.user\_id} $\rightarrow$ \texttt{users.id};
        \item \texttt{fk\_examples\_topic}: \texttt{topic\_examples.topic\_id} $\rightarrow$ \texttt{complexity\_topics.id};
        \item \texttt{fk\_saved\_user}: \texttt{user\_saved\_topics.user\_id} $\rightarrow$ \texttt{users.id};
        \item \texttt{fk\_saved\_topic}: \texttt{user\_saved\_topics.topic\_id} $\rightarrow$ \texttt{complexity\_topics.id};
        \item \texttt{fk\_log\_user}: \texttt{activity\_log.user\_id} $\rightarrow$ \texttt{users.id};
        \item \texttt{fk\_prompt\_admin}: \texttt{analysis\_prompts.updated\_by} $\rightarrow$ \texttt{users.id}.
    \end{itemize}
    \item \textbf{\texttt{UNIQUE} Constraints:}
    Prevent duplicate business keys:
    \begin{itemize}
        \item \texttt{uq\_users\_email}: Guarantees email address uniqueness across all registered users.
        \item \texttt{uq\_profile\_user}: Enforces a strict $1:1$ cardinality between users and user profiles.
        \item \texttt{uq\_topics\_slug}: Guarantees uniqueness of URL paths for curriculum topics.
        \item \texttt{uq\_saved\_user\_topic}: Guarantees that a user cannot save the same topic multiple times.
    \end{itemize}
    \item \textbf{\texttt{NOT NULL} Constraints:}
    Enforced on critical operational attributes (\texttt{email}, \texttt{password\_hash}, \texttt{time\_complexity}, \texttt{code\_text}, \texttt{topic\_name}) to prevent null value ambiguity.
    \item \textbf{Referential Actions (\texttt{ON DELETE} / \texttt{ON UPDATE}):}
    \begin{itemize}
        \item \texttt{ON DELETE CASCADE}: Applied to \texttt{user\_profiles}, \texttt{code\_analyses}, \texttt{topic\_examples}, and \texttt{user\_saved\_topics}. When a user or topic is deleted, dependent records are atomically purged.
        \item \texttt{ON DELETE SET NULL}: Applied to \texttt{analysis\_prompts(updated\_by)}. If an admin account is purged, the system retains the prompt record while safely nullifying the administrator reference.
        \item \texttt{ON UPDATE CASCADE}: Applied to all foreign keys to propagate surrogate key updates automatically.
    \end{itemize}
\end{enumerate}

\section{SQL Query Implementation}
Ten categories of complex SQL queries answering domain business questions:

\subsection{Query 1: Simple SELECT with Filtering Conditions}
\textbf{Purpose:} Retrieve all published educational topics categorized under ``Searching'' with Beginner difficulty.
\begin{lstlisting}[language=SQL]
SELECT id, topic_name, slug, difficulty, time_complexity
  FROM complexity_topics
 WHERE is_published = 1
   AND category = 'Searching'
   AND difficulty = 'Beginner';
\end{lstlisting}

\subsection{Query 2: Sorting Using ORDER BY}
\textbf{Purpose:} Retrieve saved analyses ordered by physical code line count in descending order, then by creation date.
\begin{lstlisting}[language=SQL]
SELECT id, user_id, title, language, code_lines, time_complexity, created_at
  FROM code_analyses
 ORDER BY code_lines DESC, created_at DESC
 LIMIT 10;
\end{lstlisting}

\subsection{Query 3: Aggregate Functions (COUNT, SUM, AVG, MIN, MAX)}
\textbf{Purpose:} Compute comprehensive code metrics across all analyzed snippets.
\begin{lstlisting}[language=SQL]
SELECT COUNT(*)                AS total_analyses,
       AVG(code_lines)         AS average_code_lines,
       MIN(code_lines)         AS minimum_code_lines,
       MAX(code_lines)         AS maximum_code_lines
  FROM code_analyses;
\end{lstlisting}

\subsection{Query 4: Grouping with GROUP BY and HAVING}
\textbf{Purpose:} Group analyses by time complexity class and filter for classes occurring more than twice.
\begin{lstlisting}[language=SQL]
SELECT time_complexity,
       COUNT(*) AS total_count,
       ROUND(AVG(code_lines), 1) AS avg_lines
  FROM code_analyses
 GROUP BY time_complexity
HAVING total_count >= 2
 ORDER BY total_count DESC;
\end{lstlisting}

\subsection{Query 5: Table Joins (INNER JOIN and LEFT JOIN)}
\textbf{Purpose:} Retrieve comprehensive user profile records and their current saved bookmark counts via a LEFT JOIN.
\begin{lstlisting}[language=SQL]
SELECT u.id, u.name, u.email, p.headline, p.location,
       COUNT(s.id) AS total_bookmarks
  FROM users u
  LEFT JOIN user_profiles p ON p.user_id = u.id
  LEFT JOIN user_saved_topics s ON s.user_id = u.id
 GROUP BY u.id, u.name, u.email, p.headline, p.location;
\end{lstlisting}

\subsection{Query 6: Nested Queries and Subqueries}
\textbf{Purpose:} Find all users whose personal analysis count exceeds the system-wide average.
\begin{lstlisting}[language=SQL]
SELECT id, name, email, analysis_count
  FROM users
 WHERE analysis_count > (
       SELECT AVG(analysis_count) FROM users
 );
\end{lstlisting}

\subsection{Query 7: Set Membership Using IN and EXISTS}
\textbf{Purpose:} Identify curriculum topics that have been bookmarked by at least one administrator using \texttt{EXISTS}.
\begin{lstlisting}[language=SQL]
SELECT t.id, t.topic_name, t.category
  FROM complexity_topics t
 WHERE EXISTS (
       SELECT 1
         FROM user_saved_topics s
         JOIN users u ON u.id = s.user_id
        WHERE s.topic_id = t.id
          AND u.role = 'admin'
 );
\end{lstlisting}

\subsection{Query 8: Multi-Table Join across Three Relations}
\textbf{Purpose:} Extract user names, bookmarked topic titles, and personal study notes across \texttt{users}, \texttt{user\_saved\_topics}, and \texttt{complexity\_topics}.
\begin{lstlisting}[language=SQL]
SELECT u.name AS student_name,
       t.topic_name,
       t.difficulty,
       s.note AS personal_study_note,
       s.saved_at
  FROM user_saved_topics s
  JOIN users u ON u.id = s.user_id
  JOIN complexity_topics t ON t.id = s.topic_id
 ORDER BY s.saved_at DESC;
\end{lstlisting}

\subsection{Query 9: Business Intelligence Query (Algorithmic Cost Distribution)}
\textbf{Purpose:} Aggregate analysis counts into performance cost grades (fast, moderate, heavy, severe) to inform student curriculum guidance.
\begin{lstlisting}[language=SQL]
SELECT CASE
         WHEN time_complexity IN ('O(1)', 'O(log n)') THEN 'Fast (Optimal)'
         WHEN time_complexity IN ('O(n)', 'O(n log n)') THEN 'Linear / Linearithmic'
         WHEN time_complexity IN ('O(n^2)', 'O(n^3)') THEN 'Polynomial (Heavy)'
         ELSE 'Exponential / Severe'
       END AS algorithmic_grade,
       COUNT(*) AS total_algorithms,
       ROUND(COUNT(*) * 100.0 / (SELECT COUNT(*) FROM code_analyses), 2) AS percentage_share
  FROM code_analyses
 GROUP BY algorithmic_grade
 ORDER BY total_algorithms DESC;
\end{lstlisting}

\subsection{Query 10: Database Views Implementation}
\textbf{Purpose:} Query the production view \texttt{v\_user\_overview} to render complete user dashboard credentials and calculated developer ranks.
\begin{lstlisting}[language=SQL]
SELECT id, name, email, headline, rank_label, saved_topic_count
  FROM v_user_overview
 WHERE status = 'active';
\end{lstlisting}

\section{Advanced DBMS Features}

\subsection{1. Production Database Views (5 Views)}
Five analytical views encapsulate complex joins and groupings:
\begin{itemize}
    \item \texttt{v\_user\_overview}: Joins \texttt{users} and \texttt{user\_profiles}, calculates total bookmarks, and computes dynamic rank labels (\textit{Administrator, Power analyst, Regular analyst, Newcomer}).
    \item \texttt{v\_analysis\_feed}: Combines \texttt{code\_analyses} and \texttt{users}, categorizing results into algorithmic cost grades (\textit{excellent, good, heavy, severe}).
    \item \texttt{v\_topic\_overview}: Joins \texttt{complexity\_topics} with correlated subqueries calculating total runnable examples and community bookmark counts.
    \item \texttt{v\_user\_saved\_topics}: Provides denormalized bookmark feeds with topic titles and summaries for instant dashboard loading.
    \item \texttt{v\_complexity\_distribution}: Groups analyses by time complexity buckets (\textit{fast, moderate, slow}) to power dashboard distribution telemetry.
\end{itemize}

\subsection{2. Automated Database Triggers (10 Triggers)}
Ten autonomous triggers enforce business integrity at the database engine layer:
\begin{enumerate}
    \item \texttt{trg\_users\_before\_insert}: Normalizes emails to lowercase and trims name strings.
    \item \texttt{trg\_users\_after\_insert}: Automatically creates linked \texttt{user\_profiles} with MD5 avatar seeds and logs a registration event in \texttt{activity\_log}.
    \item \texttt{trg\_users\_before\_update}: Enforces email normalization upon updates.
    \item \texttt{trg\_analyses\_after\_insert}: Increments \texttt{users.analysis\_count} and writes an audit event.
    \item \texttt{trg\_analyses\_after\_delete}: Decrements \texttt{users.analysis\_count} safely and logs the deletion.
    \item \texttt{trg\_topics\_before\_insert}: Automatically converts topic titles into URL-safe slugs.
    \item \texttt{trg\_topics\_before\_update}: Updates \texttt{updated\_at} and guarantees slug presence.
    \item \texttt{trg\_saved\_after\_insert}: Logs bookmarking actions into \texttt{activity\_log}.
    \item \texttt{trg\_saved\_after\_delete}: Logs bookmark removals into \texttt{activity\_log}.
    \item \texttt{trg\_prompt\_before\_update}: Automatically increments the prompt version integer by 1 for administrative auditing.
\end{enumerate}

\begin{lstlisting}[language=SQL]
-- Example Trigger: Auto-Increment Prompt Version on Admin Mutation
DELIMITER $$
CREATE TRIGGER trg_prompt_before_update
BEFORE UPDATE ON analysis_prompts
FOR EACH ROW
BEGIN
  SET NEW.version    = OLD.version + 1;
  SET NEW.updated_at = CURRENT_TIMESTAMP;
END$$
DELIMITER ;
\end{lstlisting}

\subsection{3. Stored Generated Columns}
In \texttt{code\_analyses}, the line count attribute is evaluated directly on-disk via MySQL's virtual generated expression:
\[
\text{code\_lines} = \text{CHAR\_LENGTH}(\text{code\_text}) - \text{CHAR\_LENGTH}(\text{REPLACE}(\text{code\_text}, \text{'\textbackslash n'}, \text{''})) + 1
\]
Marked with \texttt{STORED}, MySQL computes this integer upon tuple insertion and indexes it, avoiding run-time application parsing.

\subsection{4. ACID Transactions}
Multi-step operations execute inside strict ACID transaction boundaries:
\begin{lstlisting}[language=JavaScript]
const conn = await pool.getConnection();
try {
  await conn.beginTransaction();
  await conn.query("INSERT INTO users ...", [...]);
  // Triggers fire automatically within the transaction
  await conn.commit();
} catch (err) {
  await conn.rollback();
  throw err;
} finally {
  conn.release();
}
\end{lstlisting}

\section{Conclusion}
The ComplexityUniverse project demonstrates the successful design, normalization, cloud deployment, and full-stack integration of an industrial-grade Database Management System:
\begin{itemize}
    \item Developed a robust 9-table relational database on MySQL 8.0 strictly adhering to Boyce--Codd Normal Form (BCNF), backed by formal attribute closure proofs and minimal cover reductions.
    \item Implemented 10 autonomous database triggers enforcing domain business invariants, email normalization, audit logging, counter synchronization, and prompt version auditing.
    \item Engineered 5 analytical database views and stored generated columns to maximize dashboard query performance and eliminate runtime application overhead.
    \item Delivered a full-stack Next.js 16 application featuring React 19, Vanilla CSS design tokens, HTML5 Canvas particle graphics, and Google Gemini Generative AI integration.
    \item Enforced strict web application security via bcrypt hashing, stateless JWT authentication inside \texttt{httpOnly} cookies, and parameterized queries neutralizing SQL injection.
\end{itemize}

\section{Limitations}
\begin{enumerate}
    \item \textbf{Single-File Code Boundary:} The current implementation analyzes self-contained code snippets and functions; multi-file repository dependency graphs are not yet resolved.
    \item \textbf{External AI API Dependency:} Code complexity evaluation relies on the availability and network latency of the Google Gemini API.
    \item \textbf{Theoretical Halting Boundary:} In compliance with Rice's Theorem, code featuring highly obfuscated, non-deterministic halting behavior can only be evaluated asymptotically through probabilistic semantic reasoning.
\end{enumerate}
